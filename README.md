Tube Slide Router는 Claude Code의 요청 난이도를 `극소`·`하`·`중`·`상`·`최상`으로 판정해, 같은 대화 안에서 모델과 effort를 자동으로 고르는 플러그인입니다. 판정에는 Claude Code의 내장 `$.model.classify`를 사용하므로 별도 API 키·프록시·외부 판정 서버가 필요 없습니다. 실제 응답 모델, 토큰·캐시 사용량, 테스트 실패 기반 승급과 사후 작업 신호도 로컬 플러그인 저장소에 기록합니다.

저장소: [NuyHesHUB/tube-slide-router-plugin](https://github.com/NuyHesHUB/tube-slide-router-plugin)

## 설치와 실행

Claude Code 세션의 프롬프트에서 다음 명령으로 설치합니다.

```text
/plugin install tube-slide-router --marketplace NuyHesHUB/tube-slide-router-plugin
```

개발 중이거나 직접 로드하려면 이 저장소를 클론해 플러그인 디렉터리로 지정합니다. 이 저장소는 루트에 `.claude-plugin/plugin.json`이 있으므로 저장소 폴더 자체를 가리키면 됩니다.

```bash
git clone https://github.com/NuyHesHUB/tube-slide-router-plugin.git
claude --plugin-dir ./tube-slide-router-plugin
```

또는 저장소 폴더 안에서:

```bash
cd tube-slide-router-plugin
claude --plugin-dir .
```

## 기본 동작

기본 등급표는 다음과 같습니다.

| 등급 | 모델 | effort |
| --- | --- | --- |
| 극소 | Haiku | medium |
| 하 | Haiku | medium |
| 중 | Sonnet | medium |
| 상 | Sonnet | high |
| 최상 | Opus | high |

`중` 등급의 effort는 2026-11-20에 `high`에서 `medium`으로 낮췄습니다("싼 건 싸게, 확실할 때만 강하게"). emed1 측정(contract-v2 medium 6케이스 × {sonnet/medium, sonnet/high} × 2반복 = 24런)에서 medium·high가 **둘 다 12/12 성공**하면서 medium이 thinking 약 61%·비용 약 14%를 줄였습니다. 한계(정직): 두 effort를 **가르는 실패 케이스가 0건**이라 "측정된 손실 없이 절약"이지 모든 중 과제가 동등하다는 증명은 아닙니다. 드물게 under-think가 나면 승급 캐스케이드가 보정합니다(상세: `benchmark/real-repo-e2e/E2E-AUG1-REPORT.md` §8). 단, 분류·컨텍스트 수집이 **실패**한 불확실 경로의 안전 바닥은 이 값과 분리되어 `Sonnet/high`로 유지됩니다(불확실 = 더 사고).

기본 `modelFloor`는 `haiku`입니다(2026-11-15 변경 — 전에는 `sonnet`이었습니다). 그래서 위 표의 등급표 그대로, 극소·하 등급은 실제로 Haiku까지 내려가 실행됩니다. 이전 기본값(`sonnet`)은 R-008(2026-11-13) 때 "Haiku로 내려가면 품질이 떨어질 수 있다"는 추정으로 들어간 안전장치였는데, 그 추정에 직접적인 실측 근거는 없었습니다. R-023(2026-11-15, 저난이도 과제 4종×5반복=20건) 실험에서 `modelFloor: haiku`가 수용률 저하 없이(100%) 비용을 93.6% 줄이는 결과가 나와, 사용자가 그 결과와 "표본이 20건뿐이라 반복 검증 전"이라는 한계를 함께 확인한 뒤 기본값을 바꾸기로 결정했습니다(상세: `benchmark/rounds/R-023/R-023-report.md`). Haiku 다운그레이드를 막고 싶다면(예: 품질을 더 보수적으로 보고 싶은 팀) 설정에서 `modelFloor`를 `sonnet`으로 다시 올리면 이전 동작으로 되돌릴 수 있습니다.

첫 단계에서만 분류하고, 같은 턴의 후속 단계는 그 경로를 재사용합니다. 테스트처럼 보이는 명령이 수정 사이에 두 번 연속 실패하면 한 등급 올립니다. 작업 중에는 다시 낮추지 않습니다. 모델 전환 때 캐시가 새로 만들어지는 비용을 피하기 위해서입니다.

**턴을 넘어서도 적용되는 별개의 메커니즘이 하나 더 있습니다(keep-warm)**: 직전 턴이 더 강한
등급(예: 상)으로 처리됐다면, 바로 다음 턴이 `극소`로 분류돼도 그 강한 등급을 그대로 유지합니다
("극소로 분류됐는데 왜 상으로 처리되지?"처럼 보일 수 있는 동작이지만, **버그가 아니라 의도된
설계**입니다). 예를 들어 직전 턴에서 큰 리팩토링을 Sonnet/high로 했고, 바로 다음에 "변수 이름만
바꿔줘" 같은 사소한 질문을 하면(이것만 보면 `극소`), 그 질문은 여전히 직전의 Sonnet/high로
처리됩니다. 이렇게 하는 이유는 위 문단과 같습니다 — 모델을 내렸다가 금방 다시 올리면 그때마다
캐시가 새로 만들어지는 비용이 드는데, 극소 턴은 어느 모델로 처리하든 체감 품질 차이가 거의
없으므로 차라리 직전 등급에 얹혀가는 쪽이 더 쌉니다. `극소`가 아닌 다른 등급으로 분류되면 이
메커니즘은 적용되지 않고 정상적으로 그 등급의 라우팅이 적용됩니다. 설정에서
`keepWarmForMicro: false`로 끄면 매 턴 분류된 등급 그대로 라우팅됩니다(`mod/lib/policy.mjs`의
`decideRoute` 참고).

자동 보정(calibration)은 기본으로 꺼져 있습니다. 실제 팀 기록이 충분히 쌓인 뒤에만 설정에서 명시적으로 켜세요. 예산 가드(budget)도 기본으로 꺼져 있고, 켜면 하루 API 환산 비용이 설정 임계치(기본 경고 70%, 절약 90%, 상한 $20)를 넘을 때 등급 천장을 제한합니다.

## 명령

| 명령 | 설명 |
| --- | --- |
| `/tsr-router` | 상태와 설정 패널 열기 |
| `/tsr-router status` | 상태를 텍스트로 보기 |
| `/tsr-router off` / `on` | 현재 세션의 라우팅 끄기 / 켜기 |
| `/tsr-router pin <모델> <effort>` | 이번 세션만 즉석으로 모델/effort 고정 (설정 파일은 안 건드림, `off`보다 우선) |
| `/tsr-router unpin` | 고정 해제, 원래(auto/manual) 라우팅으로 복귀 |
| `/tsr-router setup` | 등급표·예산 설정 패널 열기 (세션 시작 시 자동으로 뜨지 않음 — 간단한 값은 `/config`, `routes`처럼 중첩된 값은 이 패널이나 설정 파일) |
| `/tsr-router export` | 팀 공유용 보정 통계를 프로젝트 파일에 내보내기 |
| `/tsr-router compare <프롬프트>` | 같은 작업을 고정 모델(기본 Sonnet/high)과 TSR 라우팅 둘 다로 실행해 비용·소요시간 비교 (1단계 구현, 아래 "비교 모드" 절 참고) |
| `/tsr-docs` | 주요 지침 문서가 가리키는 경로 존재 여부 검사 |

매 턴마다 터미널 상태줄에 `TSR {모드} · 활성 | Tier: {등급} | Routed: {모델}/{effort}`가 뜨고, 실제 서빙된 모델을 확인하면 `| 적용: {모델}`이 붙습니다(2026-11-16: "상태: model 확인됨 · effort 확인불가"/"상태: 대기" 같은 문구와 `Actual`의 `(요청값)` 표시를 없애고 `적용`으로 단순화했습니다 — 사용자 피드백: "라우터가 active 된 것만 보여주면 된다"). 2026-11-15에는 라벨을 `Selected`에서 `Routed`로 바꿨습니다 — "Selected"는 사용자가 직접 고른 것처럼 읽힐 수 있는데, 실제로는 TSR이 자동으로 고른 값이기 때문입니다. `Tier`는 분류된 난이도(극소/하/중/상/최상)로, `modelFloor` 때문에 `Routed`가 올라가도("하로 분류됐는데 Routed는 sonnet") 실제 분류 결과를 바로 알 수 있게 해줍니다. 같은 턴 안에서 승급(에스컬레이션)이 일어나면 `Tier: 하→중`처럼 이전→이후로 표시되고, 분류가 아예 일어나지 않은 경로(`pin`, `off`)에서는 `Tier` 자체가 안 뜹니다. `적용`의 모델명은 `result.usage.model`로 실제 확인된 값입니다 — effort는 `claude-code`의 `usage` 타입(`ModelUsage`/`TurnUsage`)에 필드 자체가 없어 여전히 독립적으로 검증할 방법이 없으므로(2026-11-15 재확인), 거짓 확신을 주지 않기 위해 `적용`에는 아예 표시하지 않습니다. `{모드}`는 `pin`(고정) > `off` > `auto`/`manual` 순으로 우선순위가 높은 쪽이 표시됩니다. 설정에서 `statusLine.enabled: false`로 끌 수 있습니다(라우팅 자체는 그대로 동작, 상태줄 호출만 생략).

> **hungry(예정)**: 한도가 바닥나도 가벼운 설정으로 남은 사용량을 늘려 개발을 이어가는 모드를
> 구상 중입니다. 의도했던 동작이 아직 구현되지 않아 2026-11-16 활성 명령(`/tsr-router hungry` /
> `normal`)과 패널 언급을 제거했습니다 — 내부 라우팅 로직(`mod/lib/policy.mjs` 등)은 남아
> 있지만 지금은 어떤 명령으로도 켤 수 없습니다.

### 비교 모드 (`/tsr-router compare`, 1단계 구현 — 설계: `benchmark/compare-mode-DESIGN.md`)

같은 작업을 (1) 고정 모델(기본 `claude-sonnet-5-5`/`high`, 벤치마크의 A3 기준선과 동일)과
(2) TSR 라우팅, 두 번 실행해서 비용·소요시간을 비교합니다. **직접 비용이 발생하고(두 번
실행하므로 최대 2배), 1단계 구현은 실행 전 확인 절차가 없습니다** — 명령을 치면 바로
실행됩니다.

동작 방식:
- **git 저장소에서만 지원**합니다. 커밋되지 않은 변경사항이 있으면 먼저 커밋하거나 stash
  하라는 안내와 함께 거부합니다(두 아암 모두 `HEAD` 기준 별도 git worktree에서 실행되므로,
  지금 작업 중인 미커밋 변경은 어차피 반영되지 않습니다).
- 두 아암을 **순차 실행**합니다(1단계는 병렬 아님 — 구현 단순화, 2단계에서 병렬화 예정).
- 끝나면 각 아암의 모델/effort/비용/소요시간과 **작업공간(워크트리) 경로**를 텍스트로
  보여줍니다. **결과물이 실제로 맞게 동작하는지는 자동으로 판정하지 않습니다** — 임의의
  실제 프롬프트에는 정답을 아는 채점 스크립트가 없기 때문입니다(지어낸 품질 수치를 보여주지
  않는다는 이 프로젝트의 원칙). 두 워크트리를 직접 열어 비교해보세요.
- **워크트리는 끝나도 자동으로 지우거나 원본에 병합하지 않습니다** — 결과만 보고하고, 정리는
  `git worktree remove <경로>`로 직접 해야 합니다.
- `$.process.run`의 타임아웃 상한(10분)이 그대로 적용됩니다 — 오래 걸리는 실제 작업은 10분을
  넘기면 그 아암이 실패로 처리됩니다.

## 설정

가장 가벼운 설정 경로는 Claude Code의 `/config` 메뉴입니다. 플러그인을 로드하면 `mode`(등급표 출처), `statusLineEnabled`(상태줄 표시), `calibrationEnabled`(자동 보정), `budgetEnabled`/`budgetDailyUsd`(예산 가드) 다섯 항목이 메뉴에 뜹니다. 별도 파일을 만들지 않고 바로 켜고 끌 수 있고, 값은 세션이 아니라 계정에 저장되어 다음 세션에도 유지됩니다.

`routes`(등급별 모델/effort 매핑)와 `riskAreas`는 중첩 구조라 `/config`로 표현할 수 없어, 여전히 아래 설정 파일에서만 바꿀 수 있습니다. 우선순위는 기본값 < `/config` < 프로필 파일 < 프로젝트 파일 순이며, 더 구체적인 범위가 항상 이깁니다.

프로필 설정은 `$CLAUDE_CONFIG_DIR/tube-slide-router.json`(기본값 `~/.claude/…`)에, 프로젝트 설정은 `<프로젝트>/.claude/tube-slide-router.json`에 둡니다. 프로젝트 설정이 우선합니다.

```json
{
  "version": 1,
  "mode": "manual",
  "routes": {
    "극소": { "model": "haiku", "effort": "medium" },
    "하": { "model": "haiku", "effort": "medium" },
    "중": { "model": "sonnet", "effort": "medium" },
    "상": { "model": "sonnet", "effort": "high" },
    "최상": { "model": "opus", "effort": "high" }
  },
  "budget": { "enabled": false, "dailyUsd": 20, "warnPct": 70, "savePct": 90 },
  "calibration": { "enabled": false },
  "escalation": { "cascade": true },
  "observedChecks": { "enabled": false },
  "fable": { "enabled": false },
  "statusLine": { "enabled": true }
}
```

`mode: "auto"`에서는 기본 등급표를 사용합니다. `manual`에서만 `routes`를 바꿀 수 있습니다. 팀 공유 파일 `.claude/tube-slide-router.team.json`에는 해시화한 멤버 ID와 등급별 턴·승급 수만 들어가며, 프롬프트와 파일 경로는 저장하지 않습니다.

추가 설정 키(선택):

| 키 | 기본값 | 설명 |
| --- | --- | --- |
| `escalation.cascade` | `true` | **기본 켜짐.** 반복 실패 시 한 등급씩이 아니라 FrugalGPT식으로, 추가 `failsInRow`회 실패마다 한 등급씩 더(최상까지) 비례 승급합니다. `false`로 끄면 기존의 한 번에 한 단계 승급. |
| `observedChecks.enabled` | `false` | **기본 꺼짐** — 켜면 턴 종료 후 외부 체크(CI·pre-commit·수용/테스트 러너)의 **실제** 통과/실패를 로컬 ledger에 기록해 다음 턴 승급 판단에 씁니다(관측된 실제 결과만 사용). 팀/벤치마크가 opt-in하기 전까지 대화형 라우팅은 그대로입니다. |
| `fable.enabled` | `false` | **off-by-default 레버.** 켜면 재앙 규모 위험영역(비밀정보·키, DB 마이그레이션)에 한해 상한이 opus→fable로 올라갑니다. 일반 `최상`·승급 캐스케이드는 켜도 opus 유지. fable은 **미측정** 모델이고 실가격 미상이라 비용은 `null`(미상)로 기록됩니다(0으로 지어내지 않음). `modelFloor: "fable"`도 이 키가 켜져 있어야만 적용되며, 꺼져 있으면 opus로 대체됩니다. |

## 알아두면 좋은 것

### 세션 겉보기 모델과 실제 호출 모델은 다를 수 있습니다

TSR은 **세션의 기본 모델 설정(`/model`로 바꾸는 값, 터미널 하단 상태바에 보이는 값) 자체는
건드리지 않습니다.** 대신 매 턴마다 `turn.step` 훅에서 `next({ ...e, model, effort })`로
**그 턴의 실제 API 호출만 가로채서 바꿔치기**합니다(`mod/hooks/register.ts`, 예:
201/436/492/590/753행). 즉 TSR이 개입한 뒤에도 세션 자체의 "기본 모델"이라는 값은 그대로
남아있고, 매 턴 API 호출만 TSR이 정한 모델/effort로 나갑니다.

그래서 세션 겉보기 표시(하단 상태바, 또는 모델 자신에게 "너 지금 무슨 모델이야?"라고 물어본
답변)는 TSR의 개입을 반영하지 않을 수 있습니다 — 하단 바는 세션의 기본 설정을 보여줄 뿐이고,
모델 자신의 답변도 실제로 그 턴에 어떤 모델이 응답했는지와 무관하게 신뢰할 수 없습니다(모델이
자기 자신의 정체를 정확히 아는 것도 아니고, 시스템 프롬프트에 적힌 값을 그대로 말할 수도
있습니다). **실제로 어떤 모델이 그 턴을 처리했는지 확인하려면**:
- 터미널 상태줄의 `적용: {모델}` — `result.usage.model`로 실제 확인된 값
  (effort는 여전히 독립 검증 불가라 표시하지 않습니다, 위 "명령" 절 참고).
- `.claude/tsr-telemetry.jsonl`의 `actualModel` 필드.
- Claude Code 자체의 세션 transcript(실제 요청/응답 로그).

### 보정·비용 집계는 프로젝트별로 나뉩니다 (2026-11-15부터)

- **`.claude/tsr-telemetry.jsonl`은 프로젝트별**입니다 — 프로젝트 루트 기준 하나의 파일에,
  그 프로젝트에서 도는 모든 세션이 이어붙입니다(append-only, `mod/lib/telemetry.mjs`의
  `telemetryPath(root)`, `root`는 `$.session.root()`로 구한 프로젝트 루트).
- **자동 보정(calibration)과 "오늘 비용" 집계도 2026-11-15부터 프로젝트별로 나뉩니다.**
  `$.store`는 플러그인 하나당 파일 하나라 프로젝트 구분이 원래 없는데(`types/claude-code.d.ts`
  확인), 이전까지는 그래서 **이 기기에서 돈 모든 세션의 보정·비용이 프로젝트와 무관하게
  전부 합산**됐습니다 — A 프로젝트에서 쌓은 승급 기록이 B 프로젝트의 등급 자동 상향에
  영향을 주고, A 프로젝트에서 쓴 오늘 비용이 B 프로젝트의 예산 가드 한도 계산에도 같이
  들어가는 문제였습니다(`benchmark/project-scoping-DESIGN.md`). 지금은 `tsr-cal`/`tsr-cost`
  키에 프로젝트 루트에서 계산한 짧은 해시(`mod/lib/store.mjs`의 `projectHash`, 암호학적 해시
  아님 — 단순 구분용)를 넣어 프로젝트별로 나눠 집계합니다.
- **한계 1 — 기존 데이터**: 2026-11-15 이전에 쌓인 기록(키에 프로젝트 해시가 없는 옛 형식)은
  재배정할 방법이 없습니다(애초에 어느 프로젝트 것인지 저장한 적이 없었음) — 삭제하진
  않지만 어떤 프로젝트 집계에도 더 이상 안 잡히고, 기존 정리 주기(보정 90일·비용 7일)에
  맞춰 자연히 지워집니다.
- **한계 2 — 같은 레포를 다른 경로에 또 체크아웃하면 보정이 안 이어집니다**: 프로젝트
  구분이 **경로 기준**이라서, 같은 저장소를 다른 디렉터리에 또 clone하거나 워크트리로
  체크아웃하면 다른 프로젝트로 취급됩니다 — "분명 같은 프로젝트인데 승급 기록이 안
  이어진다"고 느껴질 수 있습니다. 이 한계는 해결하지 않고 알려드리는 선에서 둡니다(경로
  대신 git 원격 URL이나 최초 커밋 해시로 묶는 대안은 복잡도가 커서 채택하지 않았습니다).
- **`/tsr-router reset`도 프로젝트 스코핑됩니다**: 보정·비용은 **이 프로젝트 것만** 지우고,
  턴·사용량·Jev 비교 기록은 (애초에 프로젝트 식별 정보가 없어서) 여전히 **이 기기 전체**를
  지웁니다 — 명령 실행 시 확인 메시지에 이 구분이 그대로 표시됩니다.
- **compare-mode(1단계 구현, `/tsr-router compare`)와의 관계**: 비교 작업은 git worktree에서
  돌고 끝나도 원본 프로젝트에 자동 병합되지 않습니다. 워크트리는 원본과 **다른 경로**라서
  `$.session.root()`도 다르게 잡히고, 그래서 compare-mode 중에 쌓인 텔레메트리·보정·비용은
  전부 그 워크트리 자신의 프로젝트 스코프(원본과는 다른 `projectHash`)에만 남습니다 — 원본
  프로젝트의 집계에는 안 섞입니다(텔레메트리는 원래도 경로 기준으로 분리돼 있었고,
  보정·비용도 이제 같은 기준으로 분리되므로 둘 다 일관되게 동작합니다).
